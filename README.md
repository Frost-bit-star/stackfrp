# stackfrp

The Vercel-hosted FRPS gateway for Stackedge.

[![Deploy with Vercel](https://vercel.com/button)](https://vercel.com/new/clone?repository-url=https%3A%2F%2Fgithub.com%2FFrost-bit-star%2Fstackfrp)

The deploy button clones this repository into Vercel and opens it ready for deployment. For a working per-app tunnel, deploy the project generated by `stackedge vercel init`; that project includes the `config.json` with its service ID and token.

This repository is the server-side deployment. It accepts public HTTP requests and relays them over an authenticated outbound WebSocket to the FRPC client built into the user's `stackedge` CLI on their own machine.

Control-plane commands (`stackedge vercel init`, `deploy`, `connect`, `probe`, `status`, `logs`, `remove`) live in the Stackedge CLI, because Stackedge is what users install locally.

## Architecture

```text
Browser ──HTTPS──> Vercel-hosted stackfrp ──WebSocket tunnel──> stackedge vercel connect on device ──HTTP──> Stackedge security proxy ──> app
```

- Each app gets its own unique service ID and bearer token, generated by `stackedge vercel init`.
- The Vercel deployment is generated from a template embedded in the Stackedge CLI.
- No Redis, database, VPS, central FRPS or incoming device connection is used.
- The device always initiates the tunnel outbound.

## Vercel runtime constraint

Vercel Functions are isolated. An in-memory tunnel registry lives in one function instance only; a later HTTP request may land in another instance with no connection to the device.

This project therefore exposes:

- `GET /_health` - deployment identity and tunnel state.
- `GET /_verify` with `x-stackfrp-token` - deployment credential check.
- `WebSocket /_frpc` - authenticated FRPC registration.
- `501` for public requests when no tunnel exists in the current instance.

Run `stackedge vercel probe <app>` on the user's machine after deployment. It reports `same-instance` only if a subsequent HTTP request sees the registered tunnel. Cross-instance routing means the deployment cannot transparently relay requests; run `server.js` on a long-lived Node runtime instead, or use a Vercel-supported persistent transport.

## Error page

The branded error page is built into `lib/error-page.js` from the supplied design. It is used for offline hosts, timeouts, oversized requests, bad configurations and other relay failures. It keeps the layout and shows "stackedge powered by frost-bit-star". Owners are directed to report issues or open pull requests at https://github.com/Frost-bit-star/stackedge.

## Configuration

A generated deployment includes `config.json`, written by `stackedge vercel init`, with the service ID and token. This lets Vercel Hobby deployments run without setting environment variables.

```json
{
  "serviceId": "svc_...",
  "token": "...",
  "application": "myapp",
  "protocol": 1,
  "maxBodySize": 16777216
}
```

Keep `config.json` private because it contains a live bearer token. Environment variables override it when needed:

```text
STACKEDGE_FRPS_SERVICE_ID
STACKEDGE_FRPS_TOKEN
STACKEDGE_FRPS_APP
STACKEDGE_FRPS_MAX_BODY_SIZE
```

## Local development

```sh
npm install
cp config.example.json config.json
# edit config.json, then:
npm start
```

`server.js` is the long-lived reference gateway; `api/gateway.js` is the Vercel entry point using the same `lib/frps` code.

## Protocol

A single byte selects the frame type:

- `1` JSON control message
- `2` request body
- `3` response body

Control messages include registration, heartbeat, request/response metadata, cancellation and errors. Bodies are binary frames tagged with a 16-byte request ID. Requests time out after 30 seconds; bodies are capped at 16 MiB.
